Section A — SQL Basics (Q1–Q6)
Q1 Display all columns and rows from the customers table › 
SELECT *
FROM   customers;

What's happening: SELECT * grabs every column. FROM customers points to the table. The asterisk (*) is a wildcard for "give me everything". In production you'd usually name columns explicitly, but for exploration this is fine.

Q2 Retrieve only first_name, last_name, and city of all customers › 
SELECT first_name,
       last_name,
       city
FROM   customers;

What's happening: Instead of *, we name exactly the three columns we need. SQL fetches only those — cheaper on bandwidth and easier to read. Think of it as "project" only the columns you care about.

Q3 List all unique categories in the products table › 
SELECT DISTINCT category
FROM            products;

What's happening: DISTINCT removes duplicate values. Without it, "Electronics" would appear once per electronics product. With it, you get each category exactly once.

Returns: Electronics, Clothing, Home
Q4 Identify the Primary Key of each table. Explain why it must be unique and NOT NULL. › 
-- Primary Keys in this schema:
-- customers   → customer_id  (INT, PK)
-- products    → product_id   (INT, PK)
-- orders      → order_id     (INT, PK)
-- order_items → item_id      (INT, PK)

-- No SQL query needed; listed from CREATE TABLE statements

Why UNIQUE? A Primary Key is the identity card of each row. If two customers shared customer_id = 101, the database wouldn't know which one an order belongs to. Uniqueness guarantees every row is identifiable without ambiguity.

Why NOT NULL? A NULL means "unknown". An unknown identity is useless — you can't link orders to a customer if the customer's ID is missing. PK = UNIQUE + NOT NULL, enforced automatically by the DB engine.

Q5 What constraints apply to the email column? What happens with a duplicate email? › 
-- From schema: email VARCHAR(100) UNIQUE NOT NULL
-- Two constraints: UNIQUE and NOT NULL

-- Attempt to insert duplicate email:
INSERT INTO customers
VALUES (109, 'Test', 'User', 'aarav.s@email.com',
        'Delhi', 'Delhi', '2024-09-01', FALSE);

-- ❌ ERROR: Duplicate entry 'aarav.s@email.com'
--    for key 'customers.email'

UNIQUE — no two rows can have the same email. The DB rejects the INSERT and throws a constraint violation error. NOT NULL — you can't skip the email field at all. Together these ensure every customer has a distinct, present email address — great for login/authentication systems.

Q6 Try inserting a product with unit_price = -50. What happens? › 
INSERT INTO products
VALUES (209, 'Faulty Item', 'Electronics',
        'TestBrand', -50.00, 100);

-- ❌ ERROR: Check constraint violated.
--    Constraint: CHECK (unit_price > 0)
--    -50 is NOT > 0, so INSERT is rejected.

CHECK constraint acts like a bouncer at the door — it evaluates the condition unit_price > 0 before any INSERT or UPDATE. Since -50 fails the check, the row is never written. This prevents bad data from entering the table in the first place, no application-level code needed.

Error: CHECK constraint violation
Section B — Filtering & Optimization (Q7–Q12)
Q7 Retrieve all orders with status = 'Delivered' › 
SELECT *
FROM   orders
WHERE  status = 'Delivered';

What's happening: WHERE filters rows before they're returned. The DB scans the orders table and only returns rows where status exactly matches 'Delivered'. The idx_orders_status index makes this fast — no full table scan needed.

Returns orders: 1001, 1002, 1004, 1006, 1008, 1010
Q8 Find all Electronics products with unit_price > ₹2000 › 
SELECT product_name,
       brand,
       unit_price
FROM   products
WHERE  category  = 'Electronics'
  AND  unit_price > 2000;

AND operator means both conditions must be true. The query first filters by category (uses idx_products_category), then further narrows to those priced above 2000.

Returns: Smart Watch (₹2999), Bluetooth Speaker (₹3499)
Q9 List customers who joined in 2024 and belong to state 'Maharashtra' › 
SELECT first_name,
       last_name,
       city,
       join_date
FROM   customers
WHERE  state     = 'Maharashtra'
  AND  join_date >= '2024-01-01'
  AND  join_date <  '2025-01-01';

Why range instead of YEAR()? Using join_date >= '2024-01-01' AND join_date < '2025-01-01' is SARGable (index-friendly). YEAR(join_date) = 2024 would wrap the column in a function, breaking the index. The range approach lets the DB use the date index directly.

Returns: Aarav Sharma (Mumbai), Karan Mehta (Pune)
Q10 Find all orders between 2024-08-10 and 2024-08-25 that are NOT cancelled › 
SELECT order_id,
       order_date,
       status,
       total_amount
FROM   orders
WHERE  order_date BETWEEN '2024-08-10' AND '2024-08-25'
  AND  status <> 'Cancelled';

BETWEEN is inclusive on both ends — same as >= '2024-08-10' AND <= '2024-08-25'. <> means "not equal to". The idx_orders_date index speeds up the date range scan.

Returns: 1004 (Delivered), 1006 (Delivered), 1007 (Pending), 1008 (Delivered), 1009 (Shipped)
Q11 Explain idx_orders_date — how it improves performance + sample query › 
-- Without index: DB reads EVERY row (full table scan)
-- O(n) — scans all orders to find date matches

-- With idx_orders_date: DB jumps directly to matching rows
-- O(log n) — like a sorted book index

-- Sample query that benefits from the index:
SELECT order_id,
       customer_id,
       total_amount
FROM   orders
WHERE  order_date >= '2024-08-15'
  AND  order_date <= '2024-08-31';

How indexes work: Think of idx_orders_date like the index at the back of a textbook. Instead of scanning every page for "August orders", the DB looks up "2024-08-15" in the sorted B-tree index and jumps straight to those rows. For large tables (millions of rows), this difference is enormous — milliseconds vs seconds.

Q12 YEAR(join_date) = 2024 — would the index be used? Rewrite as SARGable. › 
-- ❌ NOT index-friendly (wraps column in function)
SELECT * FROM customers
WHERE YEAR(join_date) = 2024;

-- ✅ SARGable — index CAN be used
SELECT * FROM customers
WHERE  join_date >= '2024-01-01'
  AND  join_date <  '2025-01-01';

SARGable = Search ARGument ABLE. When you wrap a column in YEAR(), the DB must compute that function for every row before comparing — the index on the raw column becomes useless. By rewriting to a range comparison, the column appears "naked" on the left side, so the index B-tree can be used directly. Rule of thumb: never transform the column in a WHERE clause.

YEAR() → full scan Range → index scan
Section C — Aggregation (Q13–Q18)
Q13 Count the total number of orders in the orders table › 
SELECT COUNT(*) AS total_orders
FROM   orders;

COUNT(*) counts every row regardless of NULLs. AS total_orders gives the result column a friendly name. With our sample data, this returns 10.

Result: 10
Q14 Find the total revenue (SUM of total_amount) from all 'Delivered' orders › 
SELECT SUM(total_amount) AS total_revenue
FROM   orders
WHERE  status = 'Delivered';

SUM() adds up all values in that column for the filtered rows. WHERE runs first (filtering delivered orders), then SUM() aggregates what's left.

Result: ₹18,791.00
Q15 Calculate the average unit_price of products in each category › 
SELECT   category,
         ROUND(AVG(unit_price), 2) AS avg_price
FROM     products
GROUP BY category
ORDER BY avg_price DESC;

GROUP BY splits the table into buckets by category, then AVG() computes the average price within each bucket. ROUND(..., 2) keeps it to 2 decimal places. Think of GROUP BY as "for each unique value of this column, apply the aggregate."

Electronics: ₹2224 | Clothing: ₹2699 | Home: ₹949
Q16 For each order status, find count of orders and total revenue. Sort by total revenue descending. › 
SELECT   status,
         COUNT(*) AS order_count,
         SUM(total_amount) AS total_revenue
FROM     orders
GROUP BY status
ORDER BY total_revenue DESC;

Multiple aggregates in one GROUP BY — you can apply COUNT and SUM simultaneously per group. ORDER BY runs after GROUP BY, so it can sort by the computed column total_revenue. This gives management a clean view of revenue by order stage.

Q17 Find the most expensive (MAX) and cheapest (MIN) product in each category › 
SELECT   category,
         MAX(unit_price) AS max_price,
         MIN(unit_price) AS min_price
FROM     products
GROUP BY category;

MAX() and MIN() find the extreme values per group. Combined with GROUP BY you get the price range for each category in one query. Useful for showing customers "prices starting from ₹X" per category.

Electronics: ₹899–₹3499 | Clothing: ₹799–₹4599 | Home: ₹599–₹1299
Q18 List product categories where the average unit_price is greater than ₹2000 (use HAVING) › 
SELECT   category,
         ROUND(AVG(unit_price), 2) AS avg_price
FROM     products
GROUP BY category
HAVING   AVG(unit_price) > 2000;

HAVING vs WHERE: WHERE filters individual rows before grouping. HAVING filters groups after aggregation. You can't write WHERE AVG(unit_price) > 2000 because AVG doesn't exist yet at the WHERE stage. HAVING is the "WHERE for aggregated results". Only Clothing (₹2699) qualifies here.

Result: Clothing (₹2699)
Section D — Joins & Relationships (Q19–Q23)
Q19 INNER JOIN — display each order with customer's first_name, last_name › 
SELECT o.order_id,
       o.order_date,
       c.first_name,
       c.last_name,
       o.total_amount
FROM   orders    o
INNER JOIN customers c
       ON o.customer_id = c.customer_id;

INNER JOIN returns only rows where the join condition matches in BOTH tables. We alias orders as o and customers as c for brevity. The ON clause links them via the foreign key. Result: every order gets its customer's name appended — no orphan rows, no missing rows.

Q20 LEFT JOIN — list ALL customers and their orders (NULLs for customers with no orders) › 
SELECT c.customer_id,
       c.first_name,
       c.last_name,
       o.order_id,
       o.total_amount
FROM      customers c
LEFT JOIN orders    o
          ON c.customer_id = o.customer_id;

LEFT JOIN keeps ALL rows from the left table (customers) regardless of whether a match exists in the right table (orders). Customers with no orders get NULL in order_id and total_amount columns. In our data, all 8 customers have at least one order, but in reality new or churned customers would show up with NULLs here.

Q21 3-table JOIN: orders → order_items → products showing product details per order item › 
SELECT  o.order_id,
        p.product_name,
        oi.quantity,
        oi.unit_price,
        oi.discount_pct
FROM        orders      o
INNER JOIN order_items oi
           ON o.order_id    = oi.order_id
INNER JOIN products    p
           ON oi.product_id = p.product_id
ORDER BY o.order_id;

Chaining joins: Each JOIN adds a new table. First we link orders → order_items on order_id, then link order_items → products on product_id. This follows the FK chain: orders → order_items → products. Each row in the result = one line item on one order, enriched with the product name.

Q22 Explain LEFT JOIN vs RIGHT JOIN with examples. When would you use FULL OUTER JOIN? › 
-- LEFT JOIN: all customers + matching orders
SELECT c.first_name, o.order_id
FROM      customers c
LEFT JOIN orders    o ON c.customer_id = o.customer_id;
-- → customers with NO orders appear (order_id = NULL)

-- RIGHT JOIN: all orders + matching customers
SELECT c.first_name, o.order_id
FROM       customers c
RIGHT JOIN orders    o ON c.customer_id = o.customer_id;
-- → orders with NO customer match appear (data integrity issue)

-- FULL OUTER JOIN: everything from both sides
SELECT c.first_name, o.order_id
FROM            customers c
FULL OUTER JOIN orders    o ON c.customer_id = o.customer_id;
-- → customers with no orders AND orders with no customer

LEFT JOIN — dominant side is left. All left rows appear, right side is NULL if no match. Use when: "show all customers, even those who haven't ordered yet."

RIGHT JOIN — dominant side is right. Mirror of LEFT JOIN. Rarely needed (just swap table order and use LEFT JOIN instead).

FULL OUTER JOIN — use for data quality audits: "find all orphan orders and inactive customers in one go." MySQL doesn't support FULL OUTER JOIN natively — simulate with LEFT JOIN UNION ALL RIGHT JOIN WHERE ... IS NULL.

Q23 Identify all FK relationships. What happens if you insert an order with customer_id = 999? › 
-- Foreign Key relationships in this schema:
-- orders.customer_id     → customers.customer_id
-- order_items.order_id   → orders.order_id
-- order_items.product_id → products.product_id

-- Attempt to insert order with non-existent customer:
INSERT INTO orders
VALUES (1011, 999, '2024-09-01', 'Pending', 500.00);

-- ❌ ERROR: Cannot add or update a child row:
--    a foreign key constraint fails
--    (`orders`.`customer_id` references `customers`.`customer_id`)
--    customer_id 999 does not exist in customers table

Referential Integrity: FK constraints are the database's way of enforcing "you can't have an order for a customer who doesn't exist." The DB checks whether 999 exists in customers.customer_id before allowing the INSERT into orders. Since it doesn't exist, the whole operation is rejected — no partial writes.

Why this matters: Without FK constraints, you'd have "ghost" orders pointing to deleted/non-existent customers, causing broken reports and app crashes. FKs keep your data consistent automatically.

Error: FK constraint violation Fix: Insert customer 999 first, then the order
